# Local Semantic Search for Acrobat - Implementation Specification

## Recommendation

Build this as a conventional Windows desktop application distributed as a single per-user installer. It searches every PDF currently open in Acrobat, then focuses the matching document and page. Closing the app stops the process while retaining the local indexes. Uninstalling removes application data.

The supplied document is a useful first fixture: `סיכום פנימית למבחן גמר - נגה למפל.pdf` is an A4, 289-page Hebrew/English study document generated by Word. A full text extraction with pypdf yielded 684,296 characters and Hebrew text throughout. Pages 56, 66, and 74 have very little extracted text. I rendered and reviewed these pages: each contains meaningful English tables or diagrams as images, so OCR is needed to search their embedded text. Native extraction remains the normal path; OCR should handle those pages when Tesseract is installed.

## Assessment of the initial proposal

The proposed components are generally viable, but the first implementation is overbuilt in several places:

- A separate FastAPI daemon adds local HTTP security, lifecycle, and packaging work for an app whose UI and indexer run on one machine. Use one process and a worker thread for indexing. Add an API only if a later client needs it.
- LlamaIndex's fixed hierarchical sizes do not reliably mean page/section/paragraph/sentence, and can split Hebrew passages or discard useful heading context. Start with explicit page-aware paragraph chunks and overlap. Add deeper hierarchy only if real queries show a need.
- A character-count threshold is not OCR quality detection. A sparse page can be a title or diagram; a longer extraction can still be garbage. Detect extraction failure and suspicious text, then OCR that page only.
- A database table per absolute path complicates moves and stale-index cleanup. Use one local database with a stable document ID, content fingerprint, page/chunk metadata, and replace-on-reindex behavior.
- A hotkey hook and COM automation are reliability-sensitive. Use a Windows registered hotkey and isolate Acrobat COM calls on a dedicated STA thread. Verify the exact Acrobat/Reader navigation API on the installed target; provide a visible fallback if Acrobat cannot be controlled.
- `keyboard`, FastAPI, Uvicorn, and LlamaIndex are not needed for the smallest working version. Fewer dependencies make Windows packaging and debugging easier.

## Scope and non-goals

### MVP includes

- Windows 10/11 desktop app with a normal window, installer, shortcuts, and Windows Settings uninstall entry.
- Search across all PDFs currently open in Acrobat.
- On-demand indexing with visible progress and cancellation.
- Hebrew and English mixed-language queries and passages.
- Local semantic plus lexical retrieval, returning a short excerpt and 1-based page number.
- Activating a result brings its PDF to the foreground and navigates to that page.
- Per-user local storage that persists after closing the app, with in-app index management.
- Uninstall removes the local database and downloaded model cache.

### MVP excludes

- Background folder watching, automatic indexing of every PDF, cloud services, multi-user/network service, cross-document search, answer generation, and automatic citations beyond page references.
- Guaranteed OCR of every diagram, handwriting, or complex table. OCR is a fallback for low-quality pages, not a promise of full visual understanding.
- Support for every Acrobat variant until the target installed edition is confirmed.

## Proposed architecture

```text
Windows desktop app
  ├─ Acrobat adapter (open PDFs, focus document, navigate to page)
  ├─ Qt window (search, index progress, saved index management, results)
  ├─ Application service (cross-document index state, search, navigation)
  └─ Worker thread
       ├─ PDF extractor (native text, selective OCR)
       ├─ Page-aware chunker
       ├─ Local embedder
       └─ SQLite FTS5 and vector repository
```

Use Python 3.12 and the pins in `requirements.txt`. The implementation uses PyMuPDF for extraction and page rendering, `pytesseract` plus optional Tesseract binaries/language data for fallback OCR, FastEmbed's multilingual MiniLM model for local embeddings, SQLite FTS5 and vector blobs for persistence, PySide6 for the window, and pywin32 for Windows/Acrobat integration. The model is cached in local application data and is downloaded on first use if no cache exists. `requirements-build.txt` adds PyInstaller to create the distributable installer.

The current implementation is split into:

- `main.py`: CLI and desktop window, worker threads, cross-document search, and progress UI.
- `core/service.py`: document indexing and search orchestration.
- `core/extractor.py`: native page extraction and selective OCR, returning page records and extraction diagnostics.
- `core/chunker.py`: page-preserving chunk creation with overlap.
- `core/index_store.py`: SQLite schema, FTS5, embedding adapter, vector persistence, and hybrid ranking.
- `integration/acrobat.py`: enumerate open documents, focus a chosen document, and navigate pages on an STA thread.
- `install/`: per-user installer wizard and repeatable PyInstaller build script.
- `requirements.txt`: pinned runtime dependencies.

## PDF extraction and OCR

1. Open the PDF read-only and reject unsupported, encrypted, or unavailable files with a user-readable message.
2. Extract native text per page, retaining block/line order and bounding boxes where available. Normalize Unicode to NFC, normalize line endings, and remove repeated page-number/header noise conservatively. Do not reverse Hebrew strings or apply destructive bidi rewriting; preserve logical Unicode order and let Qt render bidirectional text.
3. Record per-page character count, replacement/control-character ratio, word-like token count, and whether the page contains images. The three short pages in the sample were reviewed and contain image-only tables/diagrams with meaningful text.
4. OCR a page if native extraction is empty, nearly empty, or clearly corrupt (for example, high replacement-character/control ratio). Make thresholds configurable and log the reason. The sample's pages 56, 66, and 74 should be OCRed when Tesseract is installed.
5. Render candidate pages at 250-300 DPI, run `heb+eng`, and use OCR text only when it improves usable text. Keep OCR provenance per page/chunk. Surface a warning when Tesseract or either language pack is missing; native-text search remains usable.
6. Do not OCR every page merely because the PDF contains embedded images. Full-page OCR can duplicate correct native text and slow indexing.

## Chunking, embeddings, and retrieval

- Chunk by page first, then paragraph/blocks. Target roughly 350-600 words or 1,500-2,500 characters, with a modest 100-200 character overlap. Never merge across page boundaries in the MVP so every result has an unambiguous page. Keep shorter pages intact.
- Carry document title, page number (1-based), chunk index, heading/context text when confidently available, extraction method, and text offsets in metadata. Keep the actual chunk text retrievable for display.
- Use one local embedding model, `paraphrase-multilingual-MiniLM-L12-v2`, initially. Verify Hebrew query relevance before treating semantic search as acceptable; model choice is a measured decision, not a guarantee.
- Add SQLite FTS5 lexical retrieval alongside vector retrieval. Fuse ranked results using weighted reciprocal-rank fusion, boost contiguous query phrases, and deduplicate chunks from the same page. This protects medical terms, acronyms, drug names, and exact English/Hebrew phrases that semantic embeddings may rank poorly.
- Show the best 5 results with page, score/order, and a compact context excerpt with query terms highlighted when safe. Do not display raw similarity as a confidence percentage.
- Query embedding and search should run off the UI thread. Set an initial responsiveness target of under 2 seconds for a warm query on an ordinary recent laptop; measure on the user's machine before tuning.

## Index and persistence

- Let setup choose a parent installation location. Create the application at `<chosen location>\\AcrobatSemanticSearch` and store indexes and model files at `<chosen location>\\AcrobatSemanticSearch\\data`. Keep data after app close and remove its marked managed folder during uninstall. If the target application folder is non-empty, warn and stop before changing any files. Never modify the PDF.
- Compute `document_id` from normalized absolute path, and compute a content fingerprint from file size, modification timestamp, and preferably a streaming SHA-256. A path change should not silently return results for different content. If the file changes, mark the index stale and offer reindex.
- Store a document manifest: canonical path, display name, file fingerprint, page count, indexed time, extraction/OCR counts, embedding model and version, schema version, indexing state, and last error.
- On reindex, build a replacement set and atomically publish it only after successful completion; keep the prior index available if reindex is cancelled or fails. Deleting an index removes only local search data, never the source PDF.
- Treat paths and document text as data, not executable input. Bind the app to no network listener in the MVP.

## Acrobat integration and hotkey

- At search setup, enumerate Acrobat's open PDF documents. Perform COM automation on a dedicated single-threaded apartment (STA) thread.
- Validate the expected Acrobat edition and API calls with a small spike before building the full UI. The proposed `GetActiveDoc() -> GetPDDoc() -> GetFileName()` and JavaScript `pageNum` path should be treated as hypotheses until run against the installed Acrobat/Reader edition. Reader support may differ from Acrobat Pro.
- Navigate to Acrobat's zero-based page index derived from stored one-based page. If active-path detection or navigation is unavailable, show the result and offer an explicit fallback to open the indexed PDF and/or copy the page reference; never silently navigate another document.
- On each result activation, locate the matching open PDF again, bring it to the foreground, and navigate to its one-based page number.

## UI flow

1. The app opens to a **PDFs** tab listing files currently open in desktop Acrobat. Each row shows whether the PDF is processed, changed, or still needs processing. The user selects PDFs and chooses **Process selected PDFs** before searching.
2. The **Search** tab searches the selected, processed open PDFs. Results show the filename, page, and excerpt; clicking a result brings the correct Acrobat document forward, navigates to the page, and hides the search window to the tray.
3. If Acrobat has no open PDFs, explain how to open files in desktop Acrobat and refresh the list. Distinguish a missing COM dependency from an unavailable Acrobat installation/automation API.
4. Indexing shows phase, progress, cancel, and a useful error. Keep the app responsive. Closing the window hides it to the Windows tray; the tray menu offers **Open** and **Quit**. Only **Quit** closes services and the database.
5. If a file fingerprint changed, reprocess it before searching. **Saved indexes** lists local indexes and lets the user delete one without changing the source PDF. Closing or hiding the app keeps indexes; uninstall removes all application data.

## Security, privacy, and operations

- No cloud API, telemetry, remote daemon, or listening HTTP port in the MVP.
- Keep document text and vectors in the current Windows user's local application data. Provide a **Delete index** action and document the model cache location.
- Log operational events and errors without logging full document text or search queries by default. Add an opt-in diagnostic bundle only if needed.
- Use a single SQLite writer; serialize indexing jobs and reject duplicate simultaneous jobs for one PDF.
- Handle app shutdown during indexing cleanly; do not leave a half-published index.

## Delivery plan

### Phase 0 - feasibility spikes

1. On the target Windows install, confirm Acrobat edition, active-path detection, and navigation to a known page via COM/JavaScript.
2. Run PyMuPDF extraction on all 289 sample pages; compare the three low-text pages to rendered page content and check Hebrew order/readability.
3. Confirm the chosen FastEmbed model handles Hebrew queries, and measure first-run model download, memory, and warm query latency.
4. Confirm Tesseract `heb`/`eng` installation and OCR quality on any sample page that actually needs OCR.

### Phase 1 - searchable core

Implement extraction, page-aware chunks, local index manifest, indexing progress/cancel, hybrid retrieval, and a command-line smoke workflow. Do not add OCR until the fixture review confirms a need, but define the extractor interface for it.

### Phase 2 - Windows experience

Provide a normal desktop window, search across every open Acrobat PDF, foreground the matching document when a result is selected, and provide saved-index management. Closing the window stops the process while preserving data.

### Phase 3 - hardening and packaging

Validate reindex/cancel/recovery, file moves/changes, model cache behavior, missing OCR components, startup/shutdown, and a per-user Windows installer registered in Settings. Uninstall removes shortcuts, registration, indexes, and model cache. Sign the executable before broad distribution.

## Acceptance criteria

- The sample PDF indexes locally without altering the source. Manifest reports 289 pages and extraction/OCR provenance; indexing is repeatable and stale content is detected.
- Native extraction recovers the Hebrew/English body text on representative early, middle, and late pages. Pages 56, 66, and 74 are visually reviewed and OCR is used only where text is genuinely absent or unusable.
- A small reviewed query set covering Hebrew topics, exact English terminology/acronyms, and mixed-language queries returns a relevant page in the top five. Include representative queries such as a Hebrew topic phrase and exact English terms from the contents/body; record expected pages after manual review.
- Result page numbers match the PDF's visible one-based page numbering, including navigation to first, middle, and final pages.
- A changed PDF cannot silently use old results. Cancelled/failed reindex preserves the previous working index.
- Search and indexing do not freeze the UI; missing Tesseract, model download failure, COM failure, and encrypted/unreadable PDF each produce actionable messages.
- With network disconnected after model acquisition, extraction, embedding, search, and navigation operate locally.

## Implementation and verification status

Implemented in this folder: a Python CLI and Windows desktop window, a per-user installer build, page-aware extraction and chunking, selective OCR hooks, SQLite FTS5 plus stored FastEmbed vectors, stale-index detection, cancellation, saved-index management, and an Acrobat COM adapter that enumerates open documents and focuses a selected document before page navigation. Exact phrase ranking and Hebrew prefix expansion supplement semantic results. The PDF is opened read-only.

Previously verified against the supplied PDF: 289 pages indexed into 451 PyMuPDF chunks; real FastEmbed vectors were generated and stored. Hebrew queries for atrial fibrillation and respiratory acidosis, plus an English AF query, returned expected topic pages in the top five. Current source compiles and all three unit tests pass. The Windows installer is being built and Acrobat multi-document automation still requires a real Acrobat end-to-end check.

Not verified end to end here: Tesseract is not installed, so OCR was not run on image-only tables on pages 56, 66, and 74; the app reports these sparse pages and asks for Tesseract with Hebrew/English data. No Acrobat process was running, so COM active-document detection and page navigation still need a real check in the target Acrobat/Reader edition. The embedding model is about 220 MB and downloads on first use when not already cached.

## Open decisions before release

1. Which exact Windows edition/version is installed: Acrobat Pro, Acrobat Reader, or both?
2. Is the target one user's own computer or will this be distributed to other users? This changes installer, signing, and model provisioning.
3. Should OCR be installed as a prerequisite, bundled, or offered as an optional feature?

Recommended default: target the installed Acrobat edition first, single-user local installation, optional OCR with a clear setup check. Resolve these with the Phase 0 spikes rather than blocking core indexing work.
